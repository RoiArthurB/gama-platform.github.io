Batch Specific UI

An experiment declared with mode: batch runs the same model several times, once per set of parameter values, and drives those runs with an algorithm: the exploration, analysis or calibration method given in its method statement. Its interface is therefore different from that of a GUI experiment: it reports the progress of the runs rather than that of a single simulation, and the parameters view shows which values the method is free to change. The legacy type: batch facet is accepted with a deprecation warning; use mode: batch in new models.

Starting a batch​

A batch does not start on its own, like any experiment under the default preferences. Running it - by double-clicking its Experiment <name> | Double-click to run node in the Models view - opens the simulation perspective and loads the experiment, but leaves it waiting: the status field of the toolbar reads Batch ready. Click run to begin. and the information bar reads Experiment: 0 cycle elapsed. Press Run (the green triangle at the left of the toolbar) to launch the first run. The shipped Recipes/Define Experiments/Experiment and simulation.gaml declares autorun: true on its batch_4_simu experiment, and the launching page describes the preference of the same name, which applies to every experiment of the workspace.

The toolbar then offers, from left to right: Run, Step (one step of the current simulation), a slider for the delay between two cycles, Synchronize, Reload and Close. While the batch is running, Run becomes Pause and Step is greyed out; when the last run is over, Run, Step and the slider grey out as well, leaving Synchronize, Reload and Close available.

Information bar​

The bar at the left of the toolbar is the information bar. It turns teal while a simulation is being stepped and names that simulation, its cycle count and the time spent on it, for instance Simulation 77: 22 cycles elapsed [00:00:22]; the text it cannot show is cut off at its right edge. When nothing is stepping it falls back to the experiment level, Experiment: 24 cycles elapsed, and goes black. The bracket [hh:mm:ss] is the clock time of the current simulation, not of the batch: a batch of three hundred simulations lasts far longer than the few seconds it shows. What the batch is doing as a whole is the work of the status field at the other end of the toolbar, below.

The batch counts two things, and each part of the interface names them its own way. It visits a number of parameter sets, one after another; the facet repeat: launches each of them several times, producing the simulations the methods score. The parameters view calls the simulations Simulation runs (300 for three sets repeated a hundred times each) while the console reports the end of each set - many_not_kept | end of a run (simulations kept: 0) - and the closing message of a calibration counts the sets: Batch over. 54 runs, 3 simulations. for fifty-four candidate solutions repeated three times. Read Simulation 77 as the seventy-seventh simulation of the whole batch, not of the set currently examined, and expect the two counts to differ.

Whether a simulation is kept for later inspection is the keep_simulations: facet that decides it; the many_not_kept experiment of Tests/Batch Tests/Batch Regression.gaml runs a hundred short simulations with keep_simulations: false and parallel: 4 precisely to check that discarding them does not stall the batch, which makes it the quickest experiment to watch the interface with.

Status field​

The experiment toolbar ends, at the right of the window, with the status field: a wide text field holding a single message that says what the experiment is doing, preceded by a clock while nothing runs and by a green pair of arrows while the batch is stepping, and followed by a magnifier, a bin, and a button labelled MEM with the share of memory in use.

A batch fills it with the vocabulary of the algorithm: Batch ready. Click run to begin. when it is loaded, then Initializing simulations, Instantiating agents, the values of each simulation (infection_rate -: 0.21 dying_proba -: 0.14), Disposing Simulation 51 as its results are released, and, after every simulation that ends, the counters of the batch as a whole in the form N simulations finished | R running | W waiting (using T threads) - the message as posted by the batch agent itself, seen on screen as 7 simulations finished | 4 running | 89 w…, the tail lost at the width of the panel. The last message of a calibration reads Batch over. 54 runs, 3 simulations., and of an exploration run Batch over. 300 runs, 100 simulations.: the product counts both the sets of parameters and the simulations in those closing words, and does not use "run" the same way as the parameters view does, so a reader comparing the two should keep the two meanings apart.

The arrow at the right of the field opens it as a journal: every message the field has displayed, most recent first, each with the time at which it was posted and an icon telling who posted it - the chain glyph for the messages GAMA itself produces, a blue badge for the jobs of the platform, whose text ends with (finished), such as Console content change (finished). Both the field and the journal clip their text at the width of the panel, so the longest messages lose their tail on screen; the journal keeps the history that the field overwrites, which is what makes it worth opening when a batch behaves strangely.

The two buttons beside it belong to the workbench rather than to the experiment: the magnifier is the Search GAML reference action, and the bin asks the virtual machine to release memory - its tooltip reads Memory used: 102M over 14564M. Click to free unused memory - which posts Memory after garbage collection: 287M as a new entry of the journal.

Parameters view​

The parameters view of a batch experiment is headed with the name of the experiment it belongs to (Parameters for experiment many_not_kept0) and gathers its lines in three collapsible sections, opened one by one on their arrow or all at once with the two buttons at the right of the header. Which sections appear depends on the method driving the batch.

  • Parameters to explore lists the parameters the method varies, that is, those declared with a set of values - the among: facet, or the min:, max: and step: facets. Each line carries the label of the parameter and the value the current simulation was launched with; the values it may take are not shown. A parameter declared with init: alone keeps the same value in every run and is not listed there; the category: facet of a parameter statement groups such parameters under a heading of the model's choosing, which is how the shipped models separate the settings of the world and of the populations from the parameters under study.
  • Batch experiment gives the expression that ends a simulation, Stop condition - the one passed to until:, world.stop_sim() in the screen above.
  • The third section belongs to the method. An exploration is titled Exploration experiment and lists Exploration method (exploration), Sampling method (Exhaustive when the method visits every combination), Sampled points (the number of parameter sets the method visits) and Simulation runs (the simulations they produce: three points repeated a hundred times each give 300). An experiment that declares outputs to collect adds an Outputs of interest line; Recipes/Define Batch Experiments/Exploration.gaml does so in its exploration_with_sampling_and_outputs experiment.

A calibration is titled Calibration experiment and reports the search instead of the plan. Parameter space multiplies the number of values of each parameter, infection_rate (41) * dying_proba (20) = 820; Calibration method names the algorithm, the fitness it optimises and how a solution is scored, Method genetic | fitness = minimize nu… | min of 3 simulations for each solution, where that last figure is the repeat: facet; Best parameter set found and Best fitness give the best result so far and the values that produced it, and Last parameter set tested the pair currently being examined. The algorithm's own facets then appear as lines of their own - Population dimension, Mutation probability, Crossover probability, Preliminary number of generations and Max. number of generations for the genetic algorithm, pop_dim:, mutation_prob:, crossover_prob:, nb_prelim_gen: and max_gen: of the calibration page.

The lines that hold a result are marked with a yellow background, the parameters under study with a P. With keep_seed: true, the console prints, for every simulation, the values it was launched with and the seed that drove it - infection_rate -> 0.32 dying_proba -> 0.12 seed -> 2001550464187829250.0 - so that a solution examined twice is examined under the same draw of the random numbers.

The experiment behind the interface​

The experiment below builds on the shipped Demos/Ants (Foraging and Sorting)/models/Ant Foraging.gaml, whose global section declares the four variables the parameters act on. The exploration version, which visits every combination of the values, reads:

experiment Batch mode: batch repeat: 2 keep_seed: true
              until: (food_gathered = food_placed) or (time > 400) {
   parameter 'Size of the grid:' var: gridsize init: 75 unit: 'width and height';
   parameter 'Number:' var: ants_number init: 200 unit: 'ants';
   parameter 'Evaporation:' var: evaporation_per_cycle
            among: [0.1, 0.2, 0.5, 0.8, 1.0] unit: 'rate every cycle (1.0 means 100%)';
   parameter 'Diffusion:' var: diffusion_rate
            min: 0.1 max: 1.0 step: 0.3 unit: 'rate every cycle (1.0 means 100%)';
   method exploration;
}

gridsize and ants_number, declared with init: only, keep a fixed value; evaporation_per_cycle and diffusion_rate, given a set of values, are the parameters the method explores - five and four values, hence twenty runs of two simulations each.

Replacing the last line by method genetic maximize: food_gathered; turns the same experiment into a calibration: the method then seeks the parameter set that maximises the food gathered, and stops when a simulation reaches food_gathered = food_placed or runs for more than 400 cycles. Both listings compile in 2026-11. The fitness facets maximize: and minimize: belong to the calibration methods only: an exploration method such as exploration refuses them.

Several batch experiments ship with the release and can be opened and run directly: Recipes/Define Batch Experiments/Exploration.gaml (exploration plans, from a full factorial to explicit sets and sampling by Latin hypercube, factorial or uniform), Recipes/Define Batch Experiments/Calibration.gaml (one experiment per strategy: particle swarm, genetic, hill climbing, tabu, reactive tabu, simulated annealing) and Tests/Batch Tests/Batch Regression.gaml (short experiments that check the behaviour of runs, of until: and of threads). All three live in the batch extension: they appear in the Models view under Recipes and Tests only while it is installed.
